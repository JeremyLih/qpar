# Q-Par: hybrid CNN–QNN models under NISQ constraints

Code, run records and analysis behind "Q-Par: A Resource-Aware Composite Metric for Comparing
Hybrid CNN–QNN Models under NISQ Constraints". The study is simulation only: quantum circuits
are simulated (PennyLane `lightning.qubit` for training and noiseless evaluation, Qiskit Aer for
the noise models), latency is a simulator-cost proxy, and device noise comes from a calibrated
fake backend, not from hardware.

## What is computed

- **840 training runs** (5 seeds each): MNIST and Fashion-MNIST; a LeNet-class CNN with a 4-qubit
  quantum block placed before the convolutions (Pre), at the bottleneck (Middle) or as the head
  (Post); angle or amplitude encoding; Linear, FullyConnected or Random entanglement; training on
  20 %, 50 % or 100 % of the training pool. Baselines: the plain CNN (`base_cnn`) and a
  parameter-matched classical replacement of the quantum part (`cnn_matched`). Qubit sweep
  n ∈ {2, 4, 6, 8} for the best configuration per placement.
- **Noisy evaluation** of every hybrid run on a fixed 2,000-image test subset: the noise model of
  IBM's Heron r3 fake backend `FakeAachen` (1,024 shots) and a depolarizing sweep
  p ∈ {0.001, 0.005, 0.01, 0.02}.
- **Latency** D per configuration on one Mac (batch size 1, median of 200 samples).
- **Q-Par** = A^α (1 − σ_a)^β / [(Q/Q_max)^γ (D/D_max)^δ (G/G_max)^ε], its sensitivity to the
  exponents, the comparison with the accuracy ranking, paired tests against the matched
  baselines, and noise correlations; tables T1–T10 (LaTeX) and figures F1–F6 (PDF, PNG).

The study follows `EXPERIMENT_PROTOCOL.md`, written before the study's runs; every design choice
and deviation is recorded in `results/DECISIONS.md`, which cites the protocol by section number.
The run record (commands, instances, hours, cost, library versions, noise backend and calibration
date) is in `results/README.md`.

```
                          tables and figures from results/ (paper/README.md)
data/                     MNIST and Fashion-MNIST, downloaded by torchvision on first use
results/                  runs/ (one JSON per run), noise/ (one JSON per noisy-evaluation part),
                          latency.csv, runs.csv, summary.csv, sensitivity.csv, stats_*.csv,
                          tables/, figures/, appendix/, smoke/, fleet/ and logs/ (cloud records),
                          DECISIONS.md, README.md (the run record), STATUS
```

Not in the repository (see `.gitignore`): the datasets in `data/`, the model weights
`results/checkpoints/` (best-validation checkpoint of every run) and the resume state
`results/partial/`, all regenerated by training, and the coordinator's own state and event logs,
which hold local paths and instance IP addresses. Every CSV, table and figure can be rebuilt from
what is committed: `uv run python -m qpar.analysis` reads only `results/runs/`, `results/noise/`
and `results/latency.csv`. Re-measuring latency or re-running a noisy evaluation needs the
checkpoints, so it needs the training first.

## Reproduce everything

Requires [uv](https://docs.astral.sh/uv/) on macOS or Linux. The environment is pinned in `uv.lock`:
the script's first step, `uv sync --frozen`, installs Python 3.11 and exactly the locked package
versions (CPU-only PyTorch wheels on Linux, the PyPI wheels on macOS).

```bash
scripts/reproduce.sh cloud
```

runs environment → unit tests → smoke tests → the training and noise queue on a Lambda Cloud
fleet (needs `LAMBDA_API_KEY`, `LAMBDA_SSH_KEY_NAME` and `LAMBDA_SSH_PRIVATE_KEY_PATH`; results
sync back continuously, and each instance terminates only after a checksum-verified sync) → the
latency measurement (it asks before starting, because it needs a quiet machine) → analysis,
tables and figures.

```bash
scripts/reproduce.sh local 8
```

does the same on the local machine with 8 single-threaded workers. Both are resumable: finished
runs and noise parts are skipped.

Expected cost and time: the published run took 33.6 h of wall-clock time on 12 Lambda
`gpu_1x_a10` instances (85 instance-hours, US$110.37; the GPUs are not used). Its run records add
up to about 1,540 single-thread core-hours on those Intel Xeon 8358 cores (1,412 h of training,
126 h of evaluation), so a local run takes roughly that divided by the number of workers.
`results/README.md` has the details.

## Run a subset locally

```bash
uv sync --frozen
# one run: train, then evaluate on the test set with its best-validation checkpoint
uv run python scripts/run.py configs/matrix/mnist_post_amplitude_random_n4_tf1.0.yaml --seed 0
# its calibrated-noise and depolarizing evaluations
uv run python scripts/run.py configs/matrix/mnist_post_amplitude_random_n4_tf1.0.yaml --seed 0 --task cal
uv run python scripts/run.py configs/matrix/mnist_post_amplitude_random_n4_tf1.0.yaml --seed 0 --task depol0.01
# every unfinished job of a stage matching a config-id pattern, 4 at a time
uv run python scripts/queue.py jobs --stage main --match 'mnist_post_*_tf1.0' |
  xargs -P 4 -L 1 sh -c 'uv run python scripts/run.py "$0" --seed "$1" --task "$2"'
```

Stages are `main` (main matrices and baselines), `sweep` (after `scripts/queue.py select`) and
`noise`. `uv run python -m qpar.analysis` needs the complete study and `results/latency.csv`; for a
partial look at runs, use `qpar.analysis.load_runs()` and `summarize()` in Python.

## The paper's tables and figures

```bash
paper/build.sh
```

regenerates every table and figure of the paper from `results/`. `paper/build.sh pdf` also builds
the paper and its supplement, using the IEEE Access template files (see `paper/README.md`).

## Tests

```bash
uv run pytest
```

The first run downloads MNIST and Fashion-MNIST into `data/` (torchvision; about 145 MB on disk).
